# API OAuth2 Credential Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Add a typed Webasyst 4.2.0-compatible authorization-code and API access-token core over `wa_api_auth_codes` and `wa_api_tokens`, ready for a later HTTP/API compatibility layer.

**Architecture:** Application code owns immutable credential values, discriminated results, repository/UoW ports, credential policies, and use cases. SQLAlchemy adapters map the existing legacy tables; Webasyst-specific scope serialization, 180-second code lifetime, reusable-code compatibility behavior, token reuse, and nullable legacy fields are isolated at compatibility/persistence boundaries. HTTP extraction, redirect/consent handling, JSON/XML envelopes, and API method dispatch remain outside this slice.

**Tech Stack:** Python 3.12+, Pydantic v2, SQLAlchemy 2 async, aiosqlite/asyncmy, pytest, `secrets`.

**Spec:** `docs/superpowers/specs/2026-09-15-state-backends-api-oauth2-design.md`

## Global Constraints

- Exact supplied Webasyst Framework 4.2.0 behavior is authoritative for compatibility semantics.
- `wa_api_auth_codes` and `wa_api_tokens` remain authoritative; no replacement OAuth schema or Alembic migration is introduced.
- Authorization codes and access tokens generated by the compatibility implementation are 32 lowercase hex characters.
- Authorization-code lifetime defaults to exactly 180 seconds.
- Existing token for `(contact_id, client_id)` is reused; changed scope updates the same row/token.
- Newly-created compatibility tokens have no expiry.
- Successful token resolution updates `last_use_datetime`.
- Legacy authorization codes remain reusable until expiry; this quirk is isolated behind a policy.
- Expected misses/rejections use explicit typed variants, never `None`, `Optional`, empty values, or bool sentinels.
- Nullable legacy ORM fields are normalized immediately to explicit application states.
- No FastAPI/Starlette HTTP routes, redirects, consent UI, API method dispatch, JSON/XML envelopes, OAuth provider login, or API scope authorization is implemented here.
